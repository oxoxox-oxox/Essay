TD3 端到端导航模型：FP32/FP16/INT8 三精度吞吐对比（batch=8）
================================================================

一、方法
--------
- 模型：旧 CNN 结构 TD3（1D-CNN + action chunking），输入 obs [8,113]（lidar 100 + goal 3 + prev action 10），输出 [8,5,2]（固定 batch=8，供吞吐基准）。
- 流程：PC 训练 FP32 checkpoint -> 导出纯 FP32 ONNX（固定 batch=8）-> 目标机（Jetson Orin Nano，TRT 8.5.2.2）用 TensorRT 建 FP32/FP16/INT8 引擎。
- INT8 走 TRT 原生 PTQ：用真实 replay buffer 采样 256 条 obs 校准（batch-size=8），build_ptq_engine.py 构建 actor_int8_bs8.engine。

二、策略
--------
- 双正交技术：量化（INT8 PTQ）降低单次推理延迟 + action chunking（N=5）降低推理频率。
- 三精度公平对比：同一 actor_fp32_bs8.onnx 建三档引擎，同一 trtexec 基准流程（warmUp 200ms / duration 5s / streams=1，FP32 加 --noTF32 取真基线）。
- 每样本延迟 = 1000 / (吞吐 × batch)。
- 校准器关键点：get_batch 需返回 device 内存指针整型列表（TRT pybind 要求），不能返回 numpy array 或 host 指针。

三、背景（batch=1 实测，已存档）
-------------------------------
batch=1 下三档延迟几乎持平，FP32 反而略快（launch-bound）：
    INT8 : 7503 qps / mean 0.1298ms / p99 0.1421ms
    FP16 : 7436 qps / mean 0.1300ms / p99 0.1428ms
    FP32 : 7929 qps / mean 0.1240ms / p99 0.1396ms
根因：模型极小（MACs ≈ 208k）、batch=1 维度不对齐无法利用 Tensor Core，延迟被 kernel launch/dispatch 开销主导，砍计算量无收益。

对比例子（DQN 论文，Jetson Nano，无 Tensor Core，3 超声波 6 维状态）：
- 其 17.1ms 为端到端延迟口径，且用 PyTorch（非 TRT），FP16 优势来自框架内核/带宽/cache，与我们的 TRT 纯 GPU 计算时间口径不可比。

四、待测（batch=8）
-------------------
用固定 batch=8 的引擎复测三精度吞吐/每样本延迟，判断：
- batch=8 下 Tensor Core 是否被利用（每样本延迟是否较 batch=1 下降）；
- 量化（INT8）/FP16 是否在 batch=8 下反超 FP32，量化收益是否随 batch 增大显现。
