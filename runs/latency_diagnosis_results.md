# 导航延时诊断 · 真机实测结果（2026-08-24）

> 测量节点：`deploy/latency_node.py`（Python，/scan+/odom → obs → TRT 推理 → /cmd_vel_planner）
> 环境：Jetson Orin Nano / TRT 8.5.2.2 / FP32 bs1 引擎 / control_period=0.3s / chunk=5
> 数据：43 条决策打点（约 40s），`[timing] scan_age / obs / fwd / pub`

## 1. 各段耗时统计（毫秒）

| 环节 | 采样 | 均值 | 范围 | 说明 |
| --- | --- | --- | --- | --- |
| **scan_age**（雷达采集→决策） | 43 | **≈125** | 85–167（末条 385 为 Ctrl+C 中断） | 等待 timer 相位 + scan 周期 |
| obs（numpy 构造） | 9（仅推理 tick） | 0.80 | 0.55–1.02 | 每 5 个 tick 一次 |
| **fwd（TRT 推理，含显存拷贝）** | 9 | **1.76** | 1.28–1.94 | 每 5 个 tick 一次 |
| pub（发布） | 43 | 0.31 | 0.18–0.40 | 每个 tick |

> 注：节点实测 fwd≈1.8ms 比 bench_trt 的纯 GPU 时间（0.23ms）大，原因是节点 forward 含
> pageable 内存的 cudaMemcpy H2D/D2H（小拷贝固定开销 ~0.5-1ms/次），且无 stream 管理。

## 2. 决策周期（300ms）内的占比

| 成分 | 耗时 | 占周期 |
| --- | --- | --- |
| 等 timer（scan_age 均值） | ~125 ms | **~42%** |
| scan 间隔（12Hz 固有） | ~83 ms | ~28%（与 timer 部分重叠） |
| obs + 推理 + 发布（决策计算） | ~3 ms | **~1%** |
| 其余（调度/余量） | ~90 ms | ~30% |

## 3. 结论

1. **模型推理不是导航延时主因**：即使按含显存拷贝的实测 1.9ms 算，也只占决策周期 0.6%；
   若按纯 GPU 时间（0.23ms）仅 0.08%。
2. **延时主因是"决策周期 + timer 相位"**：scan_age 均值≈125ms（≈半周期），机器人平均要等
   约一个半周期才能处理刚到的雷达帧——这是设计使然（0.3s 定时器），与推理无关。
3. 次要因素：/scan 12Hz（~83ms 间隔）、开环 chunk（N5 → 1.5s 不重新决策）。
4. 该结论在 0.1s 周期下同样成立：fwd 1.9ms 仅占 1.9%，scan_age 均值将降至 ~50ms 仍是主导。

## 4. 若要降低"迟钝感"（与推理无关的杠杆）

| 手段 | 效果 | 代价 |
| --- | --- | --- |
| 缩短 control_period（0.3→0.1s） | scan_age 均值 125→50ms | **需重训**（step_time 同步改） |
| 事件驱动（scan 到即决策，弃 timer） | 消除相位等待，均值→~40ms | 重训 step_time≈0.083；决策率=12Hz |
| 减小 chunk（N5→N3/N1） | 开环窗口 1.5s→0.9/0.3s | 推理频率上升（无碍，余量巨大） |

## 5. 遗留观察

- 发布动作 v_ang 频繁饱和 ±1.0（最大角速度）：obs 契约或 goal 系可能未对齐训练
  （已知 obs_builder 未同步问题），不影响本次延时结论；若要真正导航需先同步 obs 构造。
- 若要把节点 fwd 压到 ~0.2ms（纯 GPU 时间）：换 pinned memory + stream，但对延时结论无影响。
